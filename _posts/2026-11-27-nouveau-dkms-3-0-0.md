`nouveau-dkms` is heading for its 3.0.0 release, and the version number is honest about what changes: the way memory reclocking works underneath is being rewritten, not patched.

## What changes in 3.0.0

Up to now, dynamic memory reclocking on Fermi has been **hardware-specific**: each supported board needed its own captured executor script, generated from NVIDIA 390.157 PMU captures and validated against that exact card. The 2.4.x line made this explicit — the DDR3 Falcon executor is gated to its specific board, and any other board logs that it has no executor script and simply keeps its boot memory clock while core, shader and voltage transitions still apply.

That model works, but it does not scale. Every new device ID means another captured script, another validation pass, another person with that card in hand.

3.0.0 migrates to **VBIOS-driven reclocking**. Instead of hardcoded per-board payloads, a generic PDAEMON `fexec` command interpreter (`wr32`, `mask`, `wait`, `nsec`, `fb_block`/`fb_unblock`, `vblank` sync) is fed by sequences built at runtime from each board's own VBIOS tables — `nvbios_rammapEm()`, `nvbios_timingEe()`, `nvkm_sddr3_calc()` for the DDR3 mode registers, `gt215_pll_calc()` for the PLL.

The consequence is the point of the whole exercise: **without shipping the actual memory training of every individual device ID, reclocking should become achievable across the entire Fermi generation.** The card brings its own programming; the driver learns to read it.

The roadmap in `TODO.md` sequences it:

1. **Phase 1** — generic DDR3 `fexec` for `GF100..GF116` and `GF108`, no board-specific scripts, validated first against known-good states on the GF106M L702X (`324 ↔ 900 MHz`) and the GF108 Quadro 600 (`324 ↔ 800 MHz`).
2. **Phase 2** — `GF119M` / `GF117M` (`410M`, GT 520M, NVS 4200M, GT 610M, 820M), accounting for their different MCLK/FB emitter behaviour.
3. **Phase 3** — Fermi GDDR5 (`GF114` GTX 560, `GF116` GTX 550 Ti), replacing hardcoded reference register values with the same VBIOS-derived path.
4. **Phase 4** — Tesla and Kepler integration, where upstream already does generic VBIOS-driven reclocking — the work there is governor integration and per-SKU safety testing.
5. **Phase 5** — universal glitchless display protection during MCLK switches.

The first slice of that is already in the tree: `0018-drm-nouveau-fermi-generic-vbios-ddr3-fexec.patch`, *"Universal resident Falcon DMEM interpreter & default VBIOS-driven DDR3 reclocking."*

## Why the hardware reports matter so much

A generic interpreter is only as good as the boards it has been proven on, and that is where the community comes in. **GitHub Discussions and hardware reports are being monitored closely** — they are not a support forum bolted onto the side of the project, they are the primary input to it.

Every dump posted there feeds directly back into the work: a ROM added to `vbios_database`, a perf table version recognised, a device ID that behaves differently from the one it was assumed to match, an emulator or laptop panel that needs a different watermark. The issue templates now point hardware telemetry at Discussions precisely because that is where the signal accumulates, while real bugs and regressions stay on the issue tracker where they can be tracked to a fix.

To everyone who has posted diagnostics, tested an alpha build on a card nobody else has, bisected a hang, or simply reported that something did or did not clock up: **thank you.** The 3.0.0 migration is being written against evidence you supplied, and the hardware list above exists because you took the time to write it down.

## Vulkan on Fermi: prototype phase, real numbers

Alongside the kernel work, `vulkan-nouveau-fermi` has reached **prototype stage** and is installable today from the AUR as **[`vulkan-nouveau-aliveos`](https://aur.archlinux.org/packages/vulkan-nouveau-aliveos)** — an open-source Vulkan driver for NVIDIA GPUs, the AliveOS NVK / Fermi research fork.

It is early, and it is already fast enough to be interesting. Measured in the Dolphin emulator, *Metal Gear Solid: The Twin Snakes* at the start of the game on the cargo dock — a scene that has always punished this class of chip — ran on regular OpenGL at roughly **10 to 20 fps**. Under Vulkan it holds a **stable 30 fps**.

For a graphics part of this vintage, that is not a rounding error; that is the difference between a slideshow and a playable game.

## nouveau-utils: fixes that may reach beyond this project

The companion userspace suite — **[`nouveau-utils`](https://aur.archlinux.org/packages/nouveau-utils)**, the dynamic frequency governor, CLI management tool and interactive TUI — has picked up a round of bug fixes and enhancements.

The notable part is what they enable elsewhere: several of these changes can help **other NVIDIA-based cards achieve dynamic reclocking even on the stock `nouveau` driver**, without the out-of-tree DKMS patches at all. That claim is provisional and **needs more testing** before anyone treats it as a guarantee — but if it holds up, the value of this work stops being confined to Fermi cards on AliveOS and starts applying to a much wider install base.
